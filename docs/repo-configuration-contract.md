# ITEM Repository Configuration Contract

## Role

ITEM is the artifact canon: the place where symbolic, visual, economic, physical, and narrative material is compressed into durable object doctrine.

ITEM should not behave like a product backlog, agent protocol, or general idea dump. Its job is selection, preservation, and artifact refinement.

## Preserve

Preserve material that does at least one of the following:

- Defines a durable artifact, unit, denomination, object, image, museum room, physical item, schema, or canonical record.
- Clarifies ITEM vs TIME, anti-entropy, artifact permanence, value preservation, or symbolic compression.
- Makes ABYS or SYNTEL more capable by giving them stable object doctrine to execute or transmit.
- Can be turned into a manufactured object, rendered asset, collectible, museum installation, canonical registry entry, or machine-readable artifact brief.

## Reinforce

Strong ITEM material should be upgraded into one of these forms:

1. Canon record in `/canon`.
2. Candidate artifact in `/candidates`.
3. Machine-readable schema in `/schemas`.
4. Artifact example in `/examples`.
5. Doctrine document in `/docs`.
6. Deprecated provenance note in `/deprecated` when historically useful but no longer governing.

## Flag or discard

Flag weak material when it is:

- Grandiose without object-level consequence.
- Mythic language that does not produce a record, artifact, schema, image grammar, denomination rule, or review decision.
- Repetition of ITEM/AETIMM slogans without additional constraint.
- Currency language that does not distinguish unit, token, minted artifact, governance, denomination, scarcity, or provenance.
- Claims of permanence that ignore maintenance, decay, versioning, custody, loss, entropy, or review.

Discard or archive material that cannot survive compression into a record.

## Canon test

A proposed ITEM addition passes only if it answers:

- What is the artifact?
- What does it preserve?
- What class does it belong to?
- What makes it resistant to entropy rather than merely decorative?
- What is its provenance?
- What can ABYS build or SYNTEL transmit because this exists?

## Boundary rule

- ITEM defines the artifact.
- ABYS builds the execution machinery.
- SYNTEL defines the inter-agent communication rail.

If a file is mainly operational, move it to ABYS.
If a file is mainly protocol or message exchange, move it to SYNTEL.
If a file is mainly artifact doctrine, keep it in ITEM.

## Immediate refactor targets

1. Convert high-signal mythic fragments into artifact briefs.
2. Move executable task logic out of ITEM and into ABYS.
3. Move message-envelope or protocol claims out of ITEM and into SYNTEL.
4. Split currency doctrine into unit ontology, issuance logic, custody/provenance, and artifact examples.
5. Keep deprecated symbolic fragments only when they document lineage.
