# AETIMM CORPUS

## Status

Canonical writing destination.

This directory is the axiomatic shelf: the continuously edited, versioned, human-readable and machine-readable product through which AETIMM can be understood, licensed, reconstructed, and instantiated.

It is not a transcript dump.
It is not a notes archive.
It is not every idea ever produced.

It is the finished system distilled from the source material.

## Product Definition

```txt
A novel's finished product is a book.
AETIMM's finished product is this corpus.
```

The corpus must be capable of answering:

- What is AETIMM?
- What is invariant?
- What may change?
- How do ITEM, ABYS, SYNTEL, ACCRE, AAA, and ANIMENTVM relate?
- What is canon, candidate, refinement, archive, and slop?
- How can another human or machine reconstruct the system?
- What rights, provenance, algorithms, schemas, and examples belong to the product?

## Source Organs

```txt
ITEM   → canon, meaning, symbolic artifacts, provenance, selection
ABYS   → execution, infrastructure, workflows, verification
SYNTEL → communication, protocols, interoperation, receipts
```

These repositories feed the corpus.
The corpus does not automatically absorb everything they contain.
Material must survive editorial judgment.

## Editorial Law

```txt
Preserve what is durable.
Refine what is promising.
Reject what is redundant, vague, inflated, misleading, or disposable.
```

The corpus itself is governed by the AETIMM-vs-SLATRA distinction:

```txt
AETIMM CORPUS = enduring, coherent, reconstructible signal
CORPUS SLOP   = repetition, mythic inflation, contradictions, dead scaffolding
```

## Writing Model

The corpus should be written like a serious book and engineered like a software specification.

Every major concept should have:

1. human-readable definition
2. formal definition
3. relationships
4. implementation implications
5. examples
6. provenance
7. status and version

## Finished-Product Test

The corpus is approaching a shelf-ready release when an unfamiliar competent reader or machine can:

1. understand AETIMM without reading the original chats;
2. distinguish doctrine from metaphor and verified implementation;
3. reconstruct the architecture;
4. validate the schemas and algorithms;
5. identify canonical artifacts;
6. trace provenance and revisions;
7. continue development without rediscovering solved questions.
